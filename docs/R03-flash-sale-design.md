# R03 限時搶購：設計說明（未實作）

> 這份文件是 R03 的**設計說明**，程式還沒有實作（PLAN 標註選做；家庭小店用不到搶購，先把設計與取捨寫清楚，之後需要再補）。
> 目的：說明「瞬間大量請求搶同一個商品」時，現在的做法會遇到什麼問題、要怎麼改、改了要付出什麼代價。

---

## 1. 現在的做法在搶購時會遇到什麼問題

### 現在（B08）怎麼扣庫存

```sql
UPDATE products SET stock = stock - :qty
WHERE id = :id AND status = 'ON_SALE' AND stock >= :qty
```

這個做法**正確**：資料庫的列鎖（row lock）保證同一時間只有一個交易能改這一列，`stock >= :qty` 保證不會扣成負數。B08 的併發測試（庫存 10、50 個執行緒同時搶）結果剛好成功 10 筆，**不會超賣**。

### 問題：正確，但在搶購時撐不住

假設 100 件商品、開賣那一秒有 5,000 個人按「搶購」：

```
5,000 個請求 ─→ 後端（200 個 Tomcat 執行緒）─→ 連線池（10 條）─→ PostgreSQL 的「同一列」
                                                                    ↑ 一次只能一個交易改
```

1. **熱點列（hot row）**：5,000 個交易都要改 `products` 的**同一列**，只能一個接一個排隊拿鎖。每個交易還要做「查商品 → 扣庫存 → 寫訂單 → 寫明細 → 寫狀態紀錄」，鎖會被握住好幾毫秒
2. **連線池被占滿**：每個排隊中的交易都佔著一條資料庫連線。預設只有 10 條，第 11 個請求開始等連線，等超過 30 秒（Hikari 預設）就失敗
3. **連帶整個網站變慢**：連線被搶購占光，**沒有參加搶購的人**（逛商品、看訂單、後台）也拿不到連線。R01 的快取能擋住商品列表，但下單、我的訂單、後台都會卡住
4. **白做工**：100 件賣完後，後面 4,900 個請求還是要進資料庫、拿鎖、發現 `stock >= :qty` 不成立才失敗。真正成功的只有 100 個，資料庫卻處理了 5,000 個

把連線池加大也沒用：瓶頸是「同一列一次只能一個交易改」，連線越多只是排隊的人越多。

**核心想法**：100 件商品只需要 100 個請求進資料庫。**在資料庫前面先決定誰搶到**，沒搶到的人在最前面就直接回應，不要碰資料庫。

## 2. 目標與非目標

| 目標 | 說明 |
|---|---|
| **不超賣** | 最重要。賣出的數量絕對不能超過活動數量 |
| **不影響網站其他部分** | 搶購期間逛商品、看訂單、後台都要正常 |
| **沒搶到的人很快得到回應** | 不要讓 4,900 個人等 30 秒才看到「已售完」 |
| **每人限購** | 例如每人 1 件，防止一個人搶光 |
| **可以解釋、可以測試** | 每個失敗情境都有明確的處理方式 |

| 非目標（刻意不做） | 理由 |
|---|---|
| 多台後端、Redis 叢集 | 一台主機的規模；設計不依賴單機，之後要擴充也適用 |
| 完全公平（先按的一定先搶到） | 網路延遲本來就不公平；只保證「名額有限、不超賣」 |
| 搶購中途改數量、改價格 | 活動開始後就鎖定，簡化一致性問題 |

## 3. 整體流程

```
                    ┌──────────────── 第一關：Redis（記憶體、單執行緒、原子操作）────────────────┐
顧客按「搶購」 ─→  │ Lua 腳本一次完成：                                                          │
POST /api/flash-   │  1. 活動進行中嗎？                    否 → 409 活動未開始／已結束            │
 sales/{id}/claim  │  2. 這個人搶過了嗎？（SET）            是 → 409 已經搶過了                   │
                    │  3. 還有名額嗎？（DECR 剩餘名額）      否 → 409 已售完（絕大多數人在這裡結束）│
                    │  4. 記錄這個人、寫入佇列（XADD）                                            │
                    └────────────────────────────────────────────────────────────────────────────┘
                                         │ 搶到了（只有 100 個人走到這裡）
                                         ▼
                    回 202 Accepted ＋ 結果查詢編號 → 前端顯示「搶到了！訂單建立中…」並輪詢結果
                                         │
                    ┌────────────────────▼───────── 第二關：背景的消費者（非同步）──────────────────┐
                    │ 從佇列一筆一筆取出，用 B08 的交易建立訂單：                                   │
                    │  - 扣資料庫的真實庫存（條件更新，最後防線）                                   │
                    │  - 建立訂單（價格用活動價）                                                   │
                    │  - flash_sale_orders 唯一約束 (活動 id, 會員 id)：同一則訊息處理兩次也只會有一筆│
                    │ 成功 → 結果寫回 Redis（訂單編號），ACK 訊息                                   │
                    │ 失敗 → 補償：Redis 名額 +1、把這個人從「搶過的人」移除，結果寫成失敗           │
                    └─────────────────────────────────────────────────────────────────────────────┘
```

### 為什麼這樣可以撐住

- **第一關在記憶體裡完成**：Redis 單執行緒、每個操作微秒等級，每秒可以處理數萬次；Lua 腳本整段原子，不需要鎖
- **只有搶到的人進資料庫**：5,000 個請求裡只有 100 個進到第二關
- **第二關的速度由消費者決定**：消費者用少量連線（例如 2 條）慢慢寫，資料庫不會被瞬間的流量打爆，其他功能照樣有連線可用。這叫**削峰填谷**（把尖峰的流量攤平）
- **顧客不用等訂單建立完**：第一關結束就回應（202），訂單在背景建立

## 4. 第一關：Redis 的資料與 Lua 腳本

### 資料

| key | 型別 | 內容 |
|---|---|---|
| `mamashop:flash:{活動id}:meta` | Hash | 開始、結束時間（活動開始前預熱寫入） |
| `mamashop:flash:{活動id}:stock` | String（數字） | 剩餘名額 |
| `mamashop:flash:{活動id}:users` | Set | 搶到的會員 id（每人限購 1 件） |
| `mamashop:flash:{活動id}:result:{會員id}` | String | 結果：`PENDING`／`SUCCESS:訂單編號`／`FAILED:原因` |
| `mamashop:flash:queue` | Stream | 待建立的訂單（給消費者） |

**預熱**：活動開始前（例如前 5 分鐘），由排程或後台按鈕把活動資料與名額從資料庫寫進 Redis。活動進行中不從資料庫讀。

### Lua 腳本（概念）

```lua
-- KEYS: meta, stock, users, result, queue    ARGV: 會員id, 現在時間, 活動id
local startsAt = tonumber(redis.call('HGET', KEYS[1], 'startsAt'))
local endsAt   = tonumber(redis.call('HGET', KEYS[1], 'endsAt'))
if not startsAt then return 'NOT_FOUND' end
local now = tonumber(ARGV[2])
if now < startsAt then return 'NOT_STARTED' end
if now > endsAt then return 'ENDED' end
if redis.call('SISMEMBER', KEYS[3], ARGV[1]) == 1 then return 'ALREADY_CLAIMED' end
if tonumber(redis.call('GET', KEYS[2])) <= 0 then return 'SOLD_OUT' end

redis.call('DECR', KEYS[2])
redis.call('SADD', KEYS[3], ARGV[1])
redis.call('SET', KEYS[4], 'PENDING', 'EX', 86400)
redis.call('XADD', KEYS[5], '*', 'eventId', ARGV[3], 'userId', ARGV[1])
return 'CLAIMED'
```

重點：

- **檢查與扣名額在同一個腳本**：和 R02 的理由一樣——分成「先 GET 再 DECR」兩個指令，兩個請求可能同時讀到「剩 1」，結果都扣，就超賣了。R02 反向驗證過：不原子的版本 10 個執行緒全部成功
- **扣名額與寫入佇列也在同一個腳本**：這是選 Redis Stream 的主要原因，見第 7 節
- 時間由後端傳入（`ARGV[2]`），不用 Redis 的時間：多台後端時以後端的時鐘為準，比較好測試（可以注入 Clock）
- 活動相關的 key 都包含同一個活動 id；如果之後用 Redis 叢集，要用 hash tag（`{flash:5}:stock`）讓它們在同一台，Lua 腳本才能一起操作

## 5. 第二關：消費者建立訂單

### 資料表（Flyway V3）

```sql
CREATE TABLE flash_sale_events (
    id             BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id     BIGINT        NOT NULL REFERENCES products (id),
    sale_price     NUMERIC(10,2) NOT NULL,
    quantity       INT           NOT NULL CHECK (quantity > 0),
    starts_at      TIMESTAMPTZ   NOT NULL,
    ends_at        TIMESTAMPTZ   NOT NULL,
    created_at     TIMESTAMPTZ   NOT NULL DEFAULT now(),
    CHECK (ends_at > starts_at)
);

-- 搶購成立的紀錄。唯一約束是「重複消費」的最後防線：同一個人在同一個活動只會有一筆
CREATE TABLE flash_sale_orders (
    event_id   BIGINT NOT NULL REFERENCES flash_sale_events (id),
    user_id    BIGINT NOT NULL REFERENCES users (id),
    order_id   BIGINT NOT NULL REFERENCES orders (id),
    PRIMARY KEY (event_id, user_id)
);
```

活動的商品庫存要**先保留**：建立活動時從商品庫存撥出 `quantity` 件（用 A02 的增減量），避免一般購買把搶購的庫存買走。

### 消費者的一筆訊息

```
1. 讀取訊息（eventId, userId）
2. 開交易：
   a. 查 flash_sale_orders 有沒有 (eventId, userId) → 有：這則訊息處理過了，直接 ACK（冪等）
   b. 建立訂單（狀態：待確認；價格：活動價；收件資訊：見第 8 節）
   c. 寫入 flash_sale_orders（唯一約束擋住同時處理同一則訊息的情況）
   d. commit
3. Redis 結果改成 SUCCESS:訂單編號
4. ACK 訊息（XACK）
```

**為什麼要冪等**：佇列只保證「至少送達一次」（at-least-once）。消費者在 commit 之後、ACK 之前當機，重啟後同一則訊息會再送一次。第 2a 步與唯一約束讓「處理兩次」的結果和「處理一次」一樣。

## 6. 失敗情境：每一種怎麼處理

| 情境 | 會發生什麼 | 處理方式 |
|---|---|---|
| 兩個人同時搶最後 1 件 | — | Lua 腳本原子，只有一個人 DECR 成功 |
| 同一個人連點、開兩個分頁 | — | `users` Set：第二次回「已經搶過了」 |
| 消費者 commit 後、ACK 前當機 | 訊息會再送一次 | 冪等（第 5 節），不會有兩筆訂單 |
| 消費者處理到一半當機（還沒 commit） | 交易 rollback，訊息沒有 ACK | Stream 的 pending list：重啟後用 `XAUTOCLAIM` 把太久沒 ACK 的訊息重新取回處理 |
| 建立訂單失敗（例如會員被停用） | 名額被佔住、使用者以為搶到了 | **補償**：Redis 名額 +1、從 `users` 移除、結果寫 `FAILED:原因`；前端顯示失敗原因 |
| 同一則訊息一直失敗 | 無限重試 | 重試 3 次後移到「死信」Stream，記 log、通知管理員人工處理（M03 的概念） |
| Redis 掛掉 | 第一關無法運作 | **活動暫停**（回 503「活動暫時無法參加」）。和 R01、R02 的「Redis 掛掉照常運作」**相反**：R01、R02 掛掉只是少了加速／保護，這裡改回直接打資料庫，就回到第 1 節的問題 |
| Redis 重啟、資料遺失 | 名額、搶過的人都不見 | Redis 開持久化（AOF）；或活動暫停後，從 `flash_sale_orders` 重新計算名額再預熱 |
| Redis 與資料庫不一致 | 例如 Redis 名額 0，資料庫只成立 98 筆 | 以資料庫為準。活動結束後對帳：`活動數量 − flash_sale_orders 筆數` 應該等於剩下的名額；差額記 log |

### 不超賣的保證有兩層

1. **Redis 名額**：DECR 到 0 之後沒有人能進第二關（主要的保證，也擋掉絕大多數請求）
2. **資料庫**：消費者建立訂單時仍然用 B08 的條件更新扣真實庫存（`stock >= :qty`）。就算 Redis 的名額算錯（例如預熱寫錯），資料庫也不會扣成負數

## 7. 佇列：Redis Stream 還是 RabbitMQ

| | Redis Stream | RabbitMQ | Kafka |
|---|---|---|---|
| 額外的服務 | 不用（R01 已經有 Redis） | 要（M 系列會加） | 要，而且比較重 |
| **扣名額和寫入佇列能不能原子** | **能**：同一個 Lua 腳本 | **不能**：Redis 和 RabbitMQ 是兩個系統 | 不能 |
| 確認機制（ACK）、當機後重新投遞 | 有（消費者群組、pending list、`XAUTOCLAIM`） | 有，而且更完整（重試、死信佇列內建） | 有（offset） |
| 訊息持久化 | 要開 AOF，預設可能遺失最後一秒 | 預設可靠（durable queue＋persistent message） | 很可靠 |
| 適合 | 小規模、已經有 Redis | 一般業務訊息（通知、背景工作） | 大量事件、需要重播 |

**推薦 Redis Stream**，主要理由是「扣名額與寫入佇列能在同一個 Lua 腳本裡原子完成」。

如果用 RabbitMQ，會遇到**雙寫問題（dual write）**：

```
1. Redis DECR 成功
2. 送訊息到 RabbitMQ ← 這時後端當機、或 RabbitMQ 連不上
→ 名額扣了，但沒有任何人會建立訂單（名額憑空消失）
```

反過來先送訊息再扣名額也一樣有問題。要解決就得加上 **Outbox 模式**（先把訊息寫進資料庫的 outbox 表，再由另一個程式送出），但這樣第一關又要寫資料庫，就失去意義了。

RabbitMQ 適合 M 系列的「訂單通知」：訊息來源是資料庫交易（訂單建立），可以用 Outbox 或「交易 commit 後送出＋失敗重試」處理，而且寄信失敗重試、死信佇列正好是 RabbitMQ 的強項。**兩者用在不同地方**，這也是面試時可以說明的取捨。

## 8. 其他設計

### 收件資訊

搶購只決定「誰拿到名額」，收件資訊有兩種做法：

- **A. 搶購時就帶收件資訊**（推薦）：請求裡附上收件人、運送方式（前端預設用會員資料），消費者直接建立完整的訂單。Lua 腳本把它們一起放進 Stream 訊息
- B. 搶到後再填：訂單先建成「待填資料」，限時 15 分鐘內填完，逾時自動取消並歸還名額（需要 M02 的延遲任務）

### 防刷

- 必須登入（JWT），每人限購 1 件（`users` Set）
- 限流：Nginx 的 `limit_req`（同一個 IP 每秒最多 N 次）或 Redis 的計數器，擋住腳本瘋狂送出
- 活動開始前不公開「搶購」API 的參數（例如活動開始時才回傳一次性的 claim token，類似 R02），避免有人提前寫好腳本
- 驗證碼：真的被刷時再加

### 前端

- 商品頁顯示倒數；時間到才可以按（前端的倒數只是體驗，真正的判斷在 Lua 腳本）
- 按下後：搶到 → 「搶到了！訂單建立中…」，每 1～2 秒輪詢 `GET /api/flash-sales/{id}/result`，成功就跳到訂單完成頁；沒搶到 → 立刻顯示「已售完」
- 按鈕送出後停用（同 F05）

## 9. 和現在（B08）的對照

| | B08（直接打資料庫） | R03（Redis 預扣＋非同步） |
|---|---|---|
| 不超賣 | ✅ 資料庫條件更新 | ✅ Redis 原子扣名額＋資料庫條件更新 |
| 瞬間大量請求 | ❌ 熱點列排隊、連線池耗盡 | ✅ 只有搶到的人進資料庫 |
| 沒搶到的人等多久 | 要等排到才知道 | 幾毫秒 |
| 影響其他功能 | ❌ 連線被占光 | ✅ 消費者只用少量連線 |
| 顧客多久看到訂單 | 立刻 | 等消費者處理（通常 1 秒內） |
| 複雜度 | 低 | 高：預熱、補償、冪等、對帳、Redis 掛掉的處理 |
| 一致性 | 強一致（一個交易） | **最終一致**（Redis 與資料庫可能短暫不同） |
| 適合 | 一般購物（本專案） | 限量、限時、瞬間流量 |

**結論**：一般購物維持 B08；只有「限量＋限時＋預期瞬間大量」的活動才值得用 R03 的做法。這也是為什麼家庭小店目前不實作。

## 11. 面試可能會問

**Q：為什麼不直接把資料庫連線池加大？**
瓶頸是「同一列一次只能一個交易改」，連線多只是排隊的人多，還會讓資料庫更忙（每條連線都要記憶體、鎖管理）。

**Q：為什麼不在 Java 裡用 synchronized 或 Redis 分散式鎖？**
`synchronized` 只在一個 JVM 有效，多台後端就失效；分散式鎖一次只讓一個請求進來，本質上還是排隊，只是把排隊從資料庫搬到 Redis。Lua 腳本不需要鎖：Redis 本身就一個一個執行指令，每個腳本微秒等級就結束。

**Q：Redis 扣了名額，但訂單沒建成怎麼辦？**
補償（名額 +1、移除搶過的紀錄、通知使用者失敗）；消費者當機則靠 Stream 的 pending list 重新投遞，加上冪等保證不會重複建立。最後以資料庫為準做對帳。

**Q：最終一致性對使用者有什麼影響？**
搶到後要等一下（通常 1 秒內）才看到訂單；極少數情況下「搶到了」最後變成失敗（補償）。所以前端要顯示「訂單建立中」，而不是直接說「購買成功」。

**Q：R01、R02 Redis 掛掉都照常運作，為什麼 R03 要暫停活動？**
R01、R02 的 Redis 是「加速」和「額外保護」，拿掉後系統還是正確的。R03 的 Redis 是「讓搶購撐得住」的核心，拿掉就回到熱點列的問題，可能拖垮整個網站；暫停一個活動，比讓整個網站掛掉好。
